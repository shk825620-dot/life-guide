# 全文搜索要不要上 Elasticsearch？

**结论：是的，你这个场景用 Elasticsearch 基本是杀鸡用牛刀。** 几万条数据、单人维护、2 核 4G 的小机器，ES 带来的资源开销和运维复杂度远超它带来的收益。

## 为什么不适合

1. **资源开销大**。ES 是 JVM 应用，堆内存一般至少给 1~2GB，加上 JVM 自身开销和 Lucene 的堆外内存，实际常驻 2G+ 很正常。你 4G 的机器还要跑应用和数据库，内存会非常紧张，稍微一查重了就可能 OOM。
2. **运维成本高**。索引 mapping 设计、分片/副本、版本升级、JVM 调参、集群健康监控……这些对单人项目全是负担，出了问题排查也费劲。
3. **数据规模差了几个数量级**。ES 的甜区是千万级以上文档、多节点、高并发查询、复杂聚合分析。几万条记录，任何嵌入式方案都能做到毫秒级响应。

## 什么时候才值得上 ES

- 数据量到千万级以上，或预计快速增长；
- 需要复杂聚合分析（类似 Kibana 那种多维统计、日志分析）；
- 有团队和专职运维，或对外提供高 QPS 的搜索服务。

这几条你一条都不沾。

## 推荐方案（按你的情况排序）

**1. SQLite FTS5（如果数据在 SQLite，或你愿意把索引放 SQLite）**
- 零额外进程，建一个虚拟表就搞定，`bm25()` 自带相关度排序；
- 几万条完全无压力（FTS5 撑到百万级都没问题）；
- 中文需要处理分词：可以用 trigram 按字切分，或挂 jieba / simple 分词扩展。

**2. 数据库自带的全文索引（如果用 MySQL / PostgreSQL）**
- MySQL：InnoDB 的 FULLTEXT 索引加 `WITH PARSER ngram`，对中文友好，不用装任何东西；
- PostgreSQL：tsvector + GIN 索引，`websearch_to_tsquery` 语法很顺手；中文要装 zhparser / pg_jieba 扩展，稍麻烦一点。

这类方案最大的好处：**搜索就是一条 SQL，没有新服务、没有新运维**，备份恢复也跟着数据库一起走。

**3. MeiliSearch（想要开箱即用的搜索体验时）**
- 单个二进制文件，Rust 写的，内存占用比 ES 小一个量级；
- 中文分词开箱即用，容错（typo tolerance）、高亮、筛选 facets 都是内置的；
- 缺点：仍然是一个独立服务，多一个要维护和备份的东西。适合前端要做"边输边搜"这类体验时再上。

**4. 实在偷懒：LIKE '%关键词%'**
- 几万条全表扫也就几十毫秒，个人项目真不一定在乎；
- 缺点是没有相关度排序、没有分词。可以先凑合，量涨了再换，不丢人。

## 我的建议

优先用你现有数据库的全文能力（方案 1 或 2），一行配置不加一个服务就能跑；如果对搜索体验（模糊容错、拼音、高亮、即时搜索）有明确要求，再考虑 MeiliSearch。**ES 在这个项目里唯一合理的位置，是等它真的长大了再说**——而且到那时候，大概率 MeiliSearch 也还够用。

最后提醒一句中文分词：用 SQLite / MySQL 方案时，记得确认分词方式（ngram / trigram 按字切分 vs jieba 类词级切分），这直接影响搜索结果质量，是这类轻量方案里唯一需要花点心思的地方。
