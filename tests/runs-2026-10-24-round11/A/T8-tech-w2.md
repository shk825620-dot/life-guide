# 几万条记录上 Elasticsearch？是的，典型的杀鸡用牛刀

直接说结论：**这个规模完全不需要 Elasticsearch**。几万条记录对现代搜索引擎来说是"玩具级"数据量，而 ES 在你这台 2 核 4G 的机器上，光"养活它自己"就要吃掉一大半资源。

## 为什么 ES 不划算

**1. 资源占用和你的机器不匹配。** ES 是 Java 服务，靠 JVM 跑。官方建议堆内存不超过物理内存的一半，而且除了堆内存在 JVM 之外还有堆外内存、mmap 文件缓存等开销。在 4G 的机器上，系统 + 你的应用 + ES，基本就顶满了。这还没算 GC 停顿、段合并这些后台行为带来的波动。

**2. 运维成本对一个独立维护者来说太高。** ES 是为集群和大数据量设计的，即使单节点你也要面对：

- index / mapping / analyzer 的概念和配置
- 版本升级时的数据迁移（ES 大版本升级经常折腾）
- 一个额外的有状态服务要备份、监控、重启后自愈
- 内存不够时它会变慢甚至崩掉 OOM，排查起来不轻松

你的项目里多一个 ES，就多一个需要持续照看的"宠物"，而不是一个即插即用的"工具"。

**3. 收益几乎为零。** 几万条记录，用任何数据库内置的全文检索，查询都是毫秒级。ES 的核心优势——分布式、水平扩展、复杂聚合分析——你一样都用不上。

## 更合适的方案（按你的实际情况选）

**方案一：直接用现有数据库的内置搜索（最省心，优先考虑）**

- **SQLite + FTS5**：如果你的数据在 SQLite 里，这是零额外服务的答案，建个 FTS5 虚拟表就行。中文分词默认不支持，但 3.34+ 自带的 trigram 分词器可以做中文子串匹配，这个数据量完全够用。
- **PostgreSQL**：`tsvector` 全文检索 + `pg_trgm` 扩展（给 `LIKE '%关键词%'` 加 GIN 索引）。中文搜索想要真正的分词可以用 zhparser 插件，但小数据量下 pg_trgm 通常就够。
- **MySQL**：FULLTEXT 索引配合内置的 ngram 解析器（5.7.6+ 自带），中文搜索可用，配置简单。

选这条路的好处：不引入任何新服务，备份就是备份数据库本身，一个人维护毫无负担。

**方案二：MeiliSearch（想要"真正的搜索体验"时的最佳替代）**

如果你要的不只是"能搜"，而是更好的搜索体验——中文分词开箱即用、拼音纠错/错别字容忍、搜索即时响应、关键词高亮、筛选面（facet）——可以看 **MeiliSearch**：

- 单个二进制文件，Rust 写的，REST API，五分钟跑起来
- 内存占用很低（几百 MB 就能跑得很好），2 核 4G 完全无压力
- 对中文的处理比 ES 默认配置好得多（ES 要装 IK 插件）

类似的还有 Typesense，定位相同。这一档是"比数据库内置搜索强很多，但比 ES 轻一个数量级"的甜点位。

**方案三：最朴素的方案**

几万条记录，如果你的查询模式很简单（比如只是标题/内容里包含关键词），甚至可以把数据加载进内存做简单匹配，或者老老实实用带索引的 `LIKE`。先问自己：我真的需要"搜索引擎"吗？很多时候答案是不需要。

## 什么时候才真的轮到 ES

给自己留个判断标准，以后满足这些条件再考虑也不迟：

- 数据量到**百万到千万级**，数据库内置搜索开始明显变慢
- 需要**复杂的聚合统计、多维 facet、按相关度精细调权**
- 有多个服务/项目要共享同一个搜索集群
- 本质上是在做日志分析（那是 ES 的老家）

## 我的建议

按维护成本从低到高排：

1. **先用现有数据库的内置全文搜索**（SQLite FTS5 / PG pg_trgm / MySQL ngram），大概率够用到项目死掉那天；
2. 想要开箱即用的中文分词和更好的搜索体验，**上 MeiliSearch**，单二进制、几百 MB 内存，对小机器非常友好；
3. **ES 留给数据量再大两个数量级的时候**——以你现在的规模和维护精力，它带来的麻烦远大于收益。

顺便提醒一句：如果你已经写了一半 ES 的代码，也不用懊恼，迁移到上面任何一个方案通常就是一两天的事，越早换越省心。
