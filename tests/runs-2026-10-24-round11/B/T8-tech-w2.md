# 结论先说

是的，你这个场景上 Elasticsearch 大概率就是杀鸡用牛刀。几万条记录、一个人打理、2 核 4G 的小机器——这三条任何一条都在把答案往"别用 ES"的方向推。

**为什么说它过重：**

1. **体量完全不匹配。** ES 的价值在于海量数据、多机分布式、复杂聚合分析这类场景。几万条记录对搜索来说是个很小的量，连最朴素的 SQL LIKE 都能扛住（单表几万行做子串匹配通常也就几十毫秒量级，这是按普通磁盘和内存的常规推断，不是实测），数据库自带的全文索引更是绰绰有余。
2. **内存吃不消。** ES 默认按机器总内存自动分配 JVM 堆，大约占到可用内存的一半（官方文档说明，2026-10-25 查证）。4G 的机器上它一启动就要走掉约 2G 的堆，堆外还有 Lucene 页缓存等开销，再算上你自己的应用和数据库，2 核 4G 会非常紧张，机器上任何其他东西都得跟着挤。
3. **负担全在你一个人身上。** JVM 调优、版本升级、安全配置、索引管理，这些活在团队里有人分摊，在个人项目里全是你的。而这个规模下，ES 那些高级能力你几乎一个都用不上。

# 更合适的选择，取决于你项目现在用什么存数据

| 你的现状 | 建议 | 说明 |
|---|---|---|
| 数据在 SQLite | 用自带的 FTS5 全文索引 | 内置的，不用装新东西。中文内容用 trigram 分词器（SQLite 3.34.0 起支持）可以做子串匹配；注意它对少于 3 个字的查询词走不了索引，短词回退用 LIKE 补就行，几万条全扫也不慢 |
| 数据在 MySQL | 用内置 FULLTEXT 索引 + ngram 解析器 | 官方内置、开箱即用，建索引时加 `WITH PARSER ngram` 即可，就是为中日韩文本设计的，默认按 2 个字切分 |
| 数据在 PostgreSQL | 用内置全文检索，配 zhparser 或 pg_jieba 做中文分词 | Postgres 原生全文检索功能很完整，中文分词靠这两个社区扩展解决；不想装扩展也可以用 pg_trgm 做子串匹配 |
| 还没定存储，或想要开箱即用的搜索体验 | 轻量级专用搜索引擎，比如 Meilisearch（类似的还有 Typesense） | 单个二进制、REST 接口、自带中文分词和容错（打错字也能搜到）、边输边出结果。内存占用随数据量增长（官方 FAQ 说明它用内存映射文件；有用户反馈约 2 万条文档占 0.7–1G 内存——这是单条用户反馈，仅供参考，不是官方数字）。2 核 4G 上跑得动，前提是你自己的应用不重 |

# 我建议的路径

1. **第一步（基本零成本）：** 直接用你现在数据库自带的全文能力。把真实数据灌进去建索引，拿你自己的典型查询试一轮，看结果质量和速度。大概率到这一步就结束了。
2. **什么时候升级到 Meilisearch 这类轻量引擎：** 当你确实需要"打错字也能搜到""边输入边出结果"这种体验，或者内置分词的搜索质量让你不满意时。迁移成本很低——几万条数据重建索引是分钟级的事。
3. **什么时候才轮到 ES：** 数据涨到百万级以上、需要复杂的多条件过滤和聚合面板、要做日志分析，或者你就是想借机学 ES 本身。到那天再上，几万条历史数据迁过去也毫无压力。

# 这个判断什么时候会被推翻

- 你的数据量预期快速增长（比如几个月内到几十万、上百万条）；
- 项目本质偏分析型，重度依赖聚合统计和多维过滤；
- 你已经有 ES 的使用经验，想往这方面发展，学习本身就是目的之一。

除此之外，"为想象中的未来规模提前买单"在个人项目里通常是亏的：现在选轻方案、将来真需要再换的代价，远小于现在就背着 ES 过日子。

# 补充几个信息可以把建议收得更准

项目用的语言和数据库、内容主要是中文还是英文、你要的搜索是"能搜到就行"还是"像 Google 那样智能"。不过不管答案是什么，"这个规模用 ES 过重"这个核心判断都不会变，变的只是上面表格里选哪一行。
