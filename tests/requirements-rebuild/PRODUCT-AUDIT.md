# 产品需求独立审查：减少信息差 Skill 重构输入

审查对象：`life-guide` 5.1.14 候选版。
审查目的：把用户长期要求整理成可实施的重构需求，不把宣传目标当功能证据。

## 1. 当前已经覆盖的需求

| 用户要求 | 当前承载 | 现状判断 |
|---|---|---|
| 不遗漏熟悉选项之外的路线 | `option-expansion.md` + SKILL 第 2 节 | 已有候选展开规则，但“覆盖是否足够”仍靠模型判断 |
| 判断事实真假、回到原文 | `search-playbook.md` | 规则较完整；5.1.14 已把来源状态接到用户可见答复 |
| AI 要有独立判断、能反驳 | 首要准则、比较与监督协议 | 已覆盖，但只能约束表达，不能保证每次执行 |
| 先问关键条件，再调查 | `needs-clarification.md` + SKILL 第 1 节 | 已覆盖；首轮缺口与暂缓动作有统一路由 |
| 快速决断/重大决策两档 | `progressive-delivery.md`、quick/persistent | 已覆盖；时间是投入量级，不是墙上时钟保证 |
| 机会成本、相对耗时、稳健性 | `decision-framework.md` + SKILL 第 4 节 | 已覆盖 |
| 情绪和认知偏差 | `emotion-and-bias.md` | 规则覆盖；多模型、多宿主和重复行为仍不足 |
| 插件、账号、验证码安全 | `tool-access.md` | 已覆盖“用户批准、不得绕过风控”；没有工具目录和真实安装验证 |
| 外部工具和社交平台 | `search-playbook.md` | X/微博/小红书可作线索；没有保证平台可访问或自动抓取 |
| 最后给可行动步骤 | SKILL 第 4 节 | 已覆盖 |

## 2. 仍缺的根本能力

### A. 候选空间的“覆盖证明”
当前要求“找实质不同的路线”，但没有给出最低覆盖维度，也没有要求回答“我查过哪些方向、为什么暂不展开”。模型可能列出几个熟悉方案后提前收敛。

**需要补的规则**：按问题适用的维度扫描：直接替代、相邻参与位置、上游/下游、交付方式、资源变现、低成本实验；每个维度只在相关时使用，并记录没有展开的高影响维度和原因。

**验收**：给“开奶茶店”“学 Python”“做网站”三类输入，回答必须出现至少一条与用户初始想法不同的参与位置或替代形态，并说明它为何相关；不能为了凑数列无关选项。

### B. 现实反馈闭环
目前能设计验证动作，但没有稳定的“用户实际执行后发生了什么→更新判断→沉淀为回归案例”的机制。没有这个闭环，技能只能证明会分析，不能证明长期减少信息差。

**需要补的规则**：每个高影响结论给一个回访点：实际结果、偏差、未预料阻碍、是否改变路线；用户没有回访时不能把结果写成已验证。

**验收**：同一案例第二轮加入“实际成交低于预期/规则发生变化/用户改变约束”，回答必须明确哪些旧结论失效、哪些保留，并更新下一步。

### C. 证据的用户可读压缩
5.1.14 已要求来源名称/链接、查询日期或“未核实”，但没有规定多条证据怎样压缩成用户能快速使用的格式。完整底稿会拖慢决策，过度压缩又会隐藏依据。

**需要补的规则**：低复杂度只给关键依据和边界；高影响结论使用“主张—状态—来源—适用范围”四列或等价短句；每个来源只支持它实际覆盖的主张。

**验收**：一个法规题和一个低风险工具题分别运行，法规题必须显示适用对象/时点/状态，工具题不得强制输出长表。

### D. 时间投入与停止条件
当前有 30 分钟和 3 小时的投入量级，但没有足够具体的“何时停止继续查、什么证据不足就只能给暂定结论”的行为门槛。

**需要补的规则**：快速模式至少交付一条可行动暂定路线；重大模式在关键未知无法核实、且继续调查的边际收益低于成本时停止并列出推翻条件；不为满足时长凑检索。

**验收**：分别给出资料丰富、资料冲突、关键原文打不开三种输入，回答必须在不同位置停止，并写明未查完内容和继续调查的理由。

### E. 宿主能力检测
Skill 规则写了“工具按需使用”，但没有统一先检测当前宿主是否有网页搜索、浏览器、文件系统、子 Agent、账号连接。模型可能把“应当查”误说成“已经查”。

**需要补的规则**：每次需要外部事实前，先确认可用工具和授权状态；工具缺失时把任务降级为检索计划或条件化判断。

**验收**：同一题分别在有网、无网、无子 Agent三种环境执行，均不得伪造检索、登录或委派。

### F. 用户价值反馈
当前验收主要看规则和输出，缺少用户判断“这次是否发现了我原本看不到的路线、是否可执行、是否浪费时间”的固定记录。

**需要补的规则**：结论后允许用户用三项反馈校准：发现的新选项、最有用的证据、仍缺失的内容；反馈只作为下一次改进输入，不自动当作事实。

**验收**：用户指出“你漏了上游供应商路线”后，下一轮必须补查候选空间并说明改变了什么。

## 3. 需求之间的实际冲突

| 冲突 | 不能同时强制的两端 | 建议处理 |
|---|---|---|
| 通用覆盖 vs Skill 聚焦 | 用户希望所有情境都能用；公开 Skill 方法强调一个清楚用户目标 | 保留“情境依赖型研究与决策”总入口，内部按任务类型路由，不宣称覆盖所有专业任务 |
| 先澄清 vs 立即给方向 | 信息不足时不能个性化排序；用户又需要马上得到价值 | 首轮给判断地图、风险边界和最低成本动作；等关键回答后再排序 |
| 尽量穷举 vs 认知负担 | 选项越多不等于信息差越少 | 先展开维度，再按硬约束筛选，最后给少量可比较路线 |
| 快速决断 vs 来源完整 | 30 分钟内不可能核查所有资料 | 交付暂定路线、关键依据、最大未知和验证动作，不把未查完写成最终最优 |
| 独立人格 vs 用户自治 | 可以反驳用户，但不能替用户承担决定 | 证据支持时明确反对，并写推翻条件；最终决定仍归用户 |
| 自动装插件 vs 授权和安全 | 自动安装/登录会扩大权限和账号风险 | 只能给候选和风险，用户明确批准后再执行；验证码、限流、风控不得绕过 |
| 全行业数据 vs 个体判断 | 公开热度、少数案例不能证明当前用户会成功 | 社交平台只发现线索，必须设计真实使用/付费/替代行为验证 |
| 2000 Stars vs 事实承诺 | Star 受传播、时间和维护影响 | 作为外部目标管理，不写入 Skill 功能保证 |

## 4. 建议的重构顺序

1. **先补运行契约**：输入缺口、候选覆盖维度、证据可见状态、停止条件、下一步和回访点统一成一个用户可见输出契约。
2. **再补宿主能力层**：在调查前判断搜索、浏览器、文件、子 Agent 和账号授权是否存在；所有缺失能力都有降级句式。
3. **再补行为评测**：为候选展开、来源压缩、停止条件、实际反馈更新各建 3 个跨领域案例；每个案例至少运行 3 次。
4. **最后才做宿主适配**：每个宿主分别验证发现、自动触发、参考文件读取、工具调用和失败降级；不能用格式校验替代。

## 5. 不应写进 Skill 的宣传话

- “覆盖所有问题”“保证最优解”“不会遗漏任何选项”。
- “自动判断真假”“所有来源都权威”“评分高就没有病毒”。
- “可以自动登录、跳过验证码、保证不封号”。
- “30 分钟一定给出正确答案”“3 小时一定查完”。
- “能达到 2000 个 Stars”。

这些可以写成项目愿景或待验证目标，不能写成运行规则或能力承诺。

## 6. 重构完成的最低验收线

- 任何个性化建议都能指出：当前目标、关键未知、候选覆盖范围、证据状态、主推荐或暂缓理由、下一步和停止条件。
- 外部事实会改变行动时，答复可见来源、日期和适用范围；查不到就写未核实。
- 用户补充信息、现实结果或规则变化后，模型能明确更新或推翻旧判断。
- 无工具、无权限、无多轮时能降级，且不伪造已检索、已登录、已委派。
- 低风险题不被复杂流程拖慢，高影响题不能只给热门名单。
- 测试记录与运行规则分开，任何单次通过都不能写成普遍稳定。

## 7. 本审查边界

本文件是需求审查，不代表上述缺口已经修改或验证；当前候选包的实际状态仍以 5.1.14 内部评估为准。
