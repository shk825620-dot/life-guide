# 通用 Skill 重构需求：工程、宿主与发布适配审查

审查对象：`skills/life-guide/` 5.1.14。
审查范围：`SKILL.md`、13 个 references、`agents/openai.yaml`、`adapters/`、`.github/workflows/`、静态校验器和 2026-10-30 内部评估。

## 结论

当前包的运行规则已经能覆盖“澄清—扩展候选—核验—比较—行动”的主链路，但它是**可手动试用的候选包**，不是已证明能在所有 Agent 中自动工作的通用产品。5.1.14 新增的“用户可见来源名称/链接、查询日期或未核实状态”只完成了规则接入和静态检查，尚未完成当前版本的真实外部来源行为验收。

最大的重构方向不是继续堆提示词，而是补三条边界：

1. **能力协商**：先判断宿主是否有浏览、搜索、文件、子 Agent、计时和登录能力，再决定能交付到哪一层。
2. **输出合同**：把每次回答的最小交付字段固定下来，减少模型漏掉来源状态、最大未知、停止条件和下一步。
3. **评测分层**：把规则静态检查、当前版本行为、宿主触发、来源真实性和用户实际效果分开计分。

## 根本缺口与重构要求

### 1. 入口范围过宽，触发边界不够可测

当前 description 把许多情境依赖型问题归入同一 Skill。OpenAI 的技能方法要求工作流对应一个可识别用户目标，并明确输入、输出、不能推断的事实、何时追问或拒绝。当前包虽然写了这些内容，但“通用决策/研究”范围很大，可能带来误触发和上下文负担。

**重构要求**：把触发分成“需要个人条件或当前证据才能判断”的主触发，以及“简单事实/纯写作不启动完整流程”的排除触发；增加 10 个应触发、5 个不应触发、5 个边界输入，分别在至少两个宿主测试。

### 2. 没有宿主能力预检

规则假设模型能搜索、浏览、读取文件或使用子 Agent，但 `SKILL.md` 没有一份首轮能力表。没有搜索工具时虽然要求“未核实”，但没有统一告诉用户当前能做到哪一步、缺什么能力、替代路线是什么。

**重构要求**：在运行开始建立能力状态：联网检索、官方页面打开、文件读取、计算、子 Agent、计时、登录/外部写入分别标记“可用/不可用/未验证”。能力不可用时自动降级交付，并把影响写入结论。

### 3. 输出合同缺少统一最小字段

多个 reference 分别要求来源、未知、下一步、机会成本和稳健性，入口有路由但没有一个唯一的短输出合同。模型可能完成一部分却省掉关键字段。

**重构要求**：建立唯一的“最小可用答复合同”：当前判断、依据状态、最大未知/分支、方案取舍、最低成本下一步、停止/改判条件。低影响问题允许省略比较字段；高影响问题不得省略来源状态和停止条件。用人工判定+少量结构探针验收，不能只数关键词。

### 4. 5.1.14 来源显示规则尚未做当前版本行为验收

当前规则要求用户可见来源名称/链接与查询日期，但现有 3×3 合成试跑针对 5.1.13，封闭材料没有外部来源。

**重构要求**：冻结 5.1.14，做真实低风险外部问题三次重复；一半输入要求能找到官方来源，一半故意提供打不开或冲突来源。逐次核对来源是否真实打开、日期是否存在、未核实是否没有被写成事实。

### 5. 社交平台线索规则完整，平台接入没有证据

X、微博、小红书已被定义为线索雷达，但没有通用 API、浏览器、登录和反爬能力。技能不能自己保证抓取、稳定访问或账号不受限。

**重构要求**：工具适配按平台单独标记能力，不把“规则支持”写成“平台可用”。每个平台至少有“无登录公开页、需要登录、遇验证码/限流”的降级测试；没有工具时提供不依赖该平台的替代调查路径。

### 6. 插件安全边界不能承诺“无病毒/不封号”

当前 `tool-access.md` 已正确拒绝这种保证，并要求用户批准安装、自己完成登录和验证码。需求计划必须把这条作为不可突破的产品边界，而不是继续寻找“自动跳过验证”的实现。

**重构要求**：插件推荐输出固定给出来源、版本、维护状态、权限、数据流、许可证、回退和未验证项；用户批准后仍不自动代替密码/验证码操作。

### 7. 候选扩展无法证明“看全了”

`option-expansion.md` 能推动从奶茶店扩展到原料、设备、维修、渠道等参与位置，但“尽所能给出所有选项”不可证明，也可能造成清单膨胀。

**重构要求**：改成“覆盖相关类别并说明搜索边界”：列出已查类别、排除类别和停止扩展理由；每个候选必须有进入条件、验证动作和失败信号。

### 8. 两档模式没有可靠计时和成本控制

30 分钟/3 小时是投入量级，模型不能保证墙上时间。当前没有统一记录调用次数、工具失败、用户等待和阶段成本的运行协议。

**重构要求**：交付每个检查点时记录“当前阶段、已用工具/资料、仍缺什么、继续的收益、停止条件”；只有宿主提供可靠计时才写实际耗时。

### 9. 评测分层仍需重构

现有静态检查很完整，行为记录很多，但当前版本、第二模型、第二宿主、真实外部来源和用户实际任务仍不齐。

**重构要求**：评测拆成五层：格式/路由、封闭材料行为、真实来源行为、宿主触发与工具、真实用户回访。每层单独通过，不允许用结构 PASS 代替行为 PASS。对高影响任务使用重复运行和人工复核，记录 pass^k 或等价的全次通过率。

## 推荐重构顺序

1. 冻结当前 5.1.14，保留历史记录；建立需求矩阵，逐条写“用户痛点—运行规则—唯一文件—验收案例—当前证据”。
2. 先补能力预检和最小输出合同，避免继续向各 reference 分散新增规则。
3. 把入口触发、候选扩展边界、两档交付和来源显示接入同一主流程。
4. 建立当前版本真实来源测试，再做两轮以上重复；失败时先判断是入口、路由、工具还是执行问题。
5. 补宿主适配测试：先 WorkBuddy 干净安装/自动触发，再选择一个标准兼容宿主；无工具时保留降级路径。
6. 最后处理发布工程：README、许可证、版本、冻结哈希、CI runner、发布包清单和用户上手案例。

## 验收标准

- 每个触发/不触发案例都有完整输入、宿主、模型、加载方式和人工判定。
- 每个高影响回答都能指出关键来源、查询日期、适用范围、未核实项和最低成本行动。
- 外部来源打不开或互相冲突时，回答会收窄、标未核实或撤回，不用搜索摘要补齐。
- 无搜索工具、无多轮、无子 Agent、遇验证码/限流时，回答给出明确降级和替代路径。
- 安装插件前列出权限和回退并等待用户批准；不会自动绕过验证码、限流或登录验证。
- 三次重复运行的高影响核心行为全部通过才记为稳定；一次通过只能记为探索性证据。
- 宿主自动触发、参考文件加载、工具调用和账号授权分别记录，不能由目录格式推断。

## 不能由 Skill 单独解决的事情

- 是否自动触发、能否读取 references、有没有联网/浏览器/子 Agent、是否支持计时：由宿主决定。
- X、微博、小红书的登录、验证码、限流和账号封禁风险：由平台、宿主和用户授权决定。
- 插件是否安全、是否含恶意代码、是否会导致账号处罚：需要来源审查、沙箱/安全工具和用户风险承担，Skill 不能作保证。
- 当前事实、地方规则、市场需求和用户真实约束：必须有可访问资料或用户提供信息，Skill 不能凭空补齐。
- 用户是否真正获益、是否愿意付费、能否达到 2,000 GitHub Stars：需要真实使用、反馈、维护和传播，不能通过提示词保证。
