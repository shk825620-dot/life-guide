## [5.0.0] - 2026-10-24 — 候选版，未发布

**按六层结构重组未知管理与监督交接，并修复三项已复现缺陷**

- **改了什么**：
  - 新增 `references/gap-map.md`（信息差地图）：十类缺口检查表（目标/现状/选项/规则/证据/口径/风险/执行/现实反馈/时间，各自路由到原有负责文件）；"重要未知三件事"明确**向用户本人确认也是核实路径**；新增"适用规则取决于未说明的属性"处理规则——先确认或给条件分支，并列引用互斥条文不算处理缺口；新增"调查中发现的新未知"跨阶段桥接与"无法多轮等待时"的降级。`SKILL.md` 第 1、3 节各加一句路由。
  - 新增 `references/supervision-protocol.md`（监督与交接）：独立监督/顺序自检/审查模式三种方式如实区分；完成证据定义（不接受口头声称、格式校验、关键词命中、"报告说完成"）；打回清单；打回时写清六件事（错误位置、影响判断、根因六类、修改位置、验证方式、保留部分）。`SKILL.md` 第 5 节加一段路由。
  - 修复 `references/search-playbook.md` 表格断裂：4.0.5 把"来源要匹配主张"段落插进了四层来源表中间，"个人观点"行被切成孤行（本机渲染检查可复现）；段落移回表格之后。同文件法规句补"条文编号与引文必须回原文，凭记忆写出的条号视同未核对，打不开原文时不给条号"。
  - `references/needs-clarification.md` 补无法多轮等待时的条件化降级；`references/decision-framework.md` 第 7 条补"向用户本人确认也是核实路径"并指向 gap-map。
  - 版本同步：`README.md`、`docs/architecture/package-boundaries.md`（后者"当前状态"此前停在 4.0.1，本次更正）。
- **为什么改**：三个行为缺口在修改前已跨模型复现——(1) 适用规则取决于服务对象年龄而未问、未给分支、未引"不再审批学龄前机构"条款：WorkBuddy 4.0.4、WorkBuddy 4.0.5、ZCode/GLM 4.0.5 共三次运行全部漏过（原"规则先确定对象"与"主动找未知"两条规则均未拦住，属未知管理无统一责任位的结构缺口）；(2) 凭记忆写法条条号：《民法典》第 734 条（实为 716 条）与《烟草专卖许可证管理办法》第 31 条（原文为"改变经营地址重新申领"）两案两模型，实质内容对、条号错，原"回到原文"句只列举了适用对象/生效时点/属地口径三项；(3) 表格断裂为 4.0.5 编辑执行错误，静态校验不查渲染。监督协议与完成证据定义对应 2026-10-22 轮"逐字输入未留档、复算脚本未留档"的记录缺陷——把该轮验收标准第七节的要求接到了运行时责任位。
- **影响文件**：新增 `references/gap-map.md`、`references/supervision-protocol.md`；修改 `SKILL.md`、`references/search-playbook.md`、`references/needs-clarification.md`、`references/decision-framework.md`、`README.md`、`docs/architecture/package-boundaries.md`、`tests/validate_package.py`（新增表格连续性检查）；新增 `tests/acceptance-criteria-5.0.0-2026-10-24.md`（新增标准，不回填历史通过）。
- **行为证据**：见 `tests/round-2026-10-24-teardown.md`。修改前（冻结副本 4.0.5，`tests/frozen-4.0.5-2026-10-24/`）与修改后（5.0.0）使用相同重建输入、相同宿主与模型（ZCode/GLM，手动加载）；另含迁移案例。修改后的判定以该轮记录为准。
- **仍未验证**：真实宿主自动触发与应用内消息测试（本会话 Computer Use 不可用，历史各轮均为手动加载运行，无一次应用内实测）；改动跨宿主稳定性；无技能对照组（业界 SkillsBench 类 with/without 对比）未做；gap-map 与监督协议仅各有一轮行为证据。

## [4.0.5] - 2026-10-22 — 候选版，未发布

**补上"测算口径"这一环（回应 2026-10-18 与 10-22 两次商业复核）**

- **改了什么**：`references/decision-framework.md` 新增一节「把测算口径先定死」七条——翻译用户目标（现金结余 ≠ 会计利润，折旧为非现金费用，不得称"含折旧的现金盈亏平衡"）；标注每个输入归属（用户提供/用户暂估当处标"未验证"/外部核实/AI 假设）；定义单位再除（营业额 ÷ 客单价 = 订单数，不等于杯数、人次、学员数）；按付款时间列现金流（已付款不计入后续月，月度平均不是日历跑道）；三种钱分开（预收款/已确认收入/可支用现金）；阈值分成本覆盖、目标达成、停止投入三条线并各自说明依据；主动找会改变选择的未知（改变哪个选择/向谁核实/现在查还是带条件）。每条结论追短链：输入及归属 → 定义/单位/时点 → 证据或假设 → 计算 → 结论与行动。
  `SKILL.md` 第四节加一句指针指向该节，不重复其内容。
  `references/search-playbook.md` 补一条「来源要匹配主张，不按网站身份一刀切」：平台抽成、转化率、存活率这类经营数字，政府答复与媒体报道只能作线索，不能作为可套用到当前门店的基准；法规须回原文核对适用对象、生效时点与属地口径。
- **为什么改**：2026-10-18 与 10-22 复核发现，正文原有"如实区分事实/用户陈述/推断/未知""规则先确定地区/对象/时间"等原则，但**没有任何一节负责测算口径本身**；而"对重要预测使用外部参照"把注意力引向外部检索。实测表现与此吻合——模型努力找本地统计与行业数据，却在基本口径上出错（把订单数写成杯数、35% 用户暂估未在当处标注、"15 万没有折旧"、把月度平均当日历跑道）。同时，原冻结验收补充把"63 杯/天"写进通过条件，**验收基准自身带入了单位错误**，且只核行为不核口径，才把口径错误判成通过。因此这不是单纯执行问题，补的是缺失环节，不是追加同义禁令。
- **影响文件**：`references/decision-framework.md`（新增一节）、`SKILL.md`（第四节一句指针）、`references/search-playbook.md`（补一段）、`CHANGELOG.md`、`README.md`。
- **同条件对比证据**：见 `tests/round-2026-10-22.md`。修改前（冻结副本 4.0.4）与修改后（4.0.5）使用相同输入、相同提示词、相同可控环境；另跑两个未见过的迁移案例。修改后出现了修改前没有的行为：输入归属表、明确"营业额÷客单价=订单数不是杯数"、现金结余不算折旧、首期租金付款方式作关键缺口给条件分支、找到成都属地预收费监管细则并说明"卖课包的钱不能拿来发工资"、季付房租的月份单独加支出。
- **仍未验证**：改动是否稳定复现（仅各一轮）、真实宿主自动触发与安装后行为、跨宿主、真实用户效用、未核实属地细则原文与若干行业数字；本轮运行中仍出现一处法条条号引用错误与一处未向用户确认的服务对象年龄缺口。校验器通过只证明包结构与格式，不证明业务结论正确。

## [4.0.3] - 2026-10-18 — 候选版，未发布

**统一 Skill 描述的兼容写法，并审计行为验收结论**

- **改了什么**：将 `SKILL.md` 的 `description` 从合法 YAML 折叠块改为等价的单行双引号字符串；同步项目状态、校验器身份说明和审计记录；新增两阶段行为验收补充。
- **为什么改**：当前 WorkBuddy 内置简化校验器用正则直接读取 `description:` 后的同一行，把 `>-` 误当成描述文本并报尖括号错误；WorkBuddy 的 OpenAI Skill Creator 与 Codex 的 YAML 感知校验器都能正确解析原写法。单行写法兼容三者，描述内容经 YAML 解析比对保持一致。
- **行为影响**：不改变运行规则、流程或推荐内容。阶段判定标准更正后，未测试行为不再记为通过。
- **验收结论更正**：关键条件不齐时先澄清符合流程，但无来源 15–20% 净利率仍是实际缺陷；高影响失败预演须在关键条件明确后复测；行为证据与事实来源质量分开判定。细节见 `tests/review-2026-10-18-workbuddy-4.0.2.md`。
- **验证**：结构检查 PASS；WorkBuddy 内置简化校验器、WorkBuddy OpenAI Skill Creator 校验器、Codex Skill Creator 校验器均输出 `Skill is valid!`；单行描述与原描述的 YAML 解析值相同（170 字符）。
- **仍未验证**：两阶段行为、真实宿主自动触发与安装后运行、跨宿主兼容、真实用户效用。

## [4.0.2] - 2026-10-18 — 候选版，未发布

**修正相邻路线检查在澄清阶段不可达的问题（本轮唯一改动）**

- **改了什么**：在 `SKILL.md` 第 1 节「识别请求与缺口」增加一条——用户已明确说出的关系或资源，即使本轮仍需澄清其他信息，也应同时检查它可能开启的相邻参与位置；并注明这属于 AI 的候选展开工作，不算提前给个人路线、排序或结论。
- **为什么改**：4.0.1 把「资源→相邻参与位置」的规则只放在调查阶段。手动加载候选内容的相邻路线测试中，模型按需求识别规则判断“缺关键信息→先澄清”，导致该项检查不可达，输出只提问、未展开任何相邻参与位置。这与更早验证中发现的同类漏项一致，说明只在后续调查阶段写规则并未改变行为。
- **影响文件**：仅 `SKILL.md` 第 1 节一条；`option-expansion.md` 细则未改（避免两处定义）。
- **重跑结果**：相邻路线测试通过（输出区分已知资源、候选线索和待验证项，并覆盖代销、分销、撮合、小批量试卖）；澄清回归通过（仍先复述、指出缺口、提问，没有提前给个人方案）。
- **验收记录（后续审计更正）**：早期验收对首轮和后续能力的判断不够严谨；首轮条件缺失时，未检索或未做完整失败预演不能证明后续能力失败。使用无来源 15–20% 净利率仍是实际问题。两阶段复测标准见 `tests/acceptance-followup-4.0.2.md`；审计见 `tests/review-2026-10-18-workbuddy-4.0.2.md`。
- **验证**：`python -X utf8 tests/validate_package.py` → `Structural package check: PASS`。`quick_validate.py` 对 frontmatter 的 `description: >-`（合法 YAML 折叠块标量）报 `Description cannot contain angle brackets`，属该脚本对 YAML 语法的误报；本轮未改 frontmatter 格式，请负责人决定处置方式。
- **仍未验证**：两阶段行为、真实宿主自动触发、安装后运行、跨宿主、真实用户效用。
