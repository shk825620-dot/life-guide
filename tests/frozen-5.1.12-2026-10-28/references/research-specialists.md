# 按需专题研究角色库

这是一组可委派的任务卡，不是五个常驻 Agent，也不是必须安装的五个 Skill。它们对应五类真实的信息遗漏：候选太窄、已有方案漏查、事实/时效不准、规则例外漏看、建议不可行动。

## 调用规则

- 先按 `needs-clarification.md` 确保个性化研究有足够的用户目标和条件；专才不能替用户猜目的。
- 只有调查结果可能改变重要判断，且子任务边界清楚时才启用相关角色。**简单、稳定、低影响问题不调用专才**；不要为了“完整”启动全部角色。
- 任务可彼此独立时才并行；有先后依赖时顺序执行。每个角色只拿到完成任务所需的信息。
- 角色发现是线索，不是事实认证。主 Agent 回查足以改变推荐的关键主张，处理分歧并负责最后比较、推荐和答复。
- 宿主未提供独立子 Agent 时，可由主 Agent 按角色任务逐项自检，但必须说明这是同一 Agent 的顺序检查，不是独立复核。
- 不以多数票处理冲突，不因角色数量制造确定性，不自动安装插件，不传递密码、Cookie、Token 或无关私人材料。

## 五类角色

### 角色一：选项空间侦察员

**要解决的痛点：** 用户或 AI 只在熟悉、热门的几个选项里挑，真正可选的路线尚未展开。

**任务：** 从用户目标出发，查找实质不同的解决形态、参与位置和进入路径。商业问题可按客户、上下游、耗材、设备、渠道、流通、维护和配套服务等相关维度观察；学习、生活和工作问题要换成本领域相干的维度。

**交付：** 少量值得核查的实质不同路径；确有多少列多少，不为达到固定数目制造候选。每条写明解决谁的问题、为何可能相关、支持证据或待验证假设、适用条件。标出仍未覆盖的相关类别。

**边界：** 不追求穷举；不把“原料、设备”等名词直接说成商机，不把新奇当成更优，也不从个别案例推导普遍需求。复用 `option-expansion.md`。

### 角色二：成熟方案与复用侦察员

**要解决的痛点：** 用户打算从零开始，但可能已有工具、服务、模板、开源项目或成熟流程能更省时地解决问题。

**任务：** 针对问题寻找可直接采用或组合的现成路径，检查它实际解决什么、维护状态、许可、价格、所需技能/权限、数据限制、迁移和退出成本。若用户说“仿做网站”，调查范围应包括现成建站工具、模板、可复用组件、外包/服务与自主开发，而非直接进入编码。

**交付：** 最值得比较的现成路径、原始来源、实际限制、适用条件，以及相对“自己从头做”的差异；若未找到合适项，说明查过的范围和不足。

**边界：** 不把 GitHub 星数、宣传语或搜索排名当成熟度或效果证明；不执行未经授权的安装、登录、购买或外部写入。复用 `search-playbook.md` 和 `tool-access.md`。

### 角色三：主张、来源与时效审计员

**要解决的痛点：** 版本过时、引文拼接、来源不支持结论、搜索摘要被当原文。

**任务：** 只审查会影响路线或结论的关键主张；回到最接近原始的来源，核查原文、上下文、日期、版本、范围和是否存在反证。先判断信息是否易变，再决定是否需要当前查询。

**交付：** 被审主张、可定位来源与核查日期、来源真正支持的内容、不支持的部分、冲突/未知，以及对建议的影响。

**边界：** 不为静态常识强行实时检索；不拼接引文；不能核实就缩小结论，不用引用数量伪装可靠。复用 `search-playbook.md`。

### 角色四：规则、门槛与例外调查员

**要解决的痛点：** 只看到一般规则，遗漏法域、对象、时间、资格、定义、门槛、豁免或设备代际。

**任务：** 先明确适用地区/法域和对象，再检查正式规则或原始说明中的适用范围、定义、例外、过渡条款与执行条件。产品/设备建议则核查型号、版本、年代和影响结论的机制差异。

**交付：** 当前能确认的规则、适用范围、与用户情形的对应关系、可能改变结论的例外和仍需补充的事实；区分正式文本与实际执行证据。

**边界：** 不把其他地区或旧版本套进来，不把“未找到”说成“不存在”，不把资料核查包装成专业法律意见。

### 角色五：现实可行性与失败预演审查员

**要解决的痛点：** 建议听起来合理，却卡在成本、能力、时间、权限、获客、前置条件或退出代价上。

**任务：** 按用户已说条件，找出会阻断执行的关键前提；拆出现金和时间成本、技能/许可、资源获取方式、依赖、失败损失和可逆性。重要预测有可比数据时检查外部基准；没有就不造概率。对高影响方案做简短失败预演，给出关键假设、早期信号、最低成本验证以及继续、调整或停止条件。商业问题区分客户需求证据、用户假设和待收集数据。

**交付：** 现在可试 / 补齐明确条件后可试 / 当前不适用的判断与理由；最关键未知、一个可执行的小试、观察指标和停止条件。

**边界：** 不编造本地市场规模、成本、转化率或收入；不把小样本测试夸大为成功保证。复用 `decision-framework.md`。

## 统一交接格式

每个角色只交与任务有关的结果：

1. **任务范围：** 检查了什么、没检查什么。
2. **关键发现：** 事实、用户提供的信息、推断和待验证假设分开。
3. **证据：** 来源链接/名称、日期和可定位位置；重要引文保留上下文。
4. **适用条件：** 地区、对象、版本、时间、权限和资源等。
5. **反证与未知：** 哪些内容会削弱结论，哪些尚未核实。
6. **决策影响：** 哪项新信息会改变路线、筛选或推荐。
7. **下一步：** 最小可执行的查证或现实试验。

主 Agent 不复制角色输出当最终答案；先去重、回查关键依据，再按用户条件形成单一清楚的比较与建议。角色之间出现冲突时回到来源和适用条件，不投票。

## 设计依据与限制

角色拆分借鉴了按问题分解任务、价值链观察、形态分析和按风险匹配评估力度等公开方法；它们只提供调查视角，不证明某条业务路径有需求，也不保证角色运行提升结果。五类角色来自本项目已记录的真实失败类型与用户提出的痛点，后续是否有效必须在真实宿主和实际任务中验证。
