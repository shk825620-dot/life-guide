# 减少信息差：按需研究专才库设计规格

- 日期：2026-10-18
- 状态：设计已在 4.0.0 候选版实施；本文件保留设计依据与验收范围，运行规则以 `skills/life-guide/references/research-specialists.md` 为准
- 基线：工作区对外说明与需求记录中的 life-guide 3.3.0
- 本稿范围：在现有通用 Skill 中加入一套可按需调用的研究专才角色与调度规则
- 实施原则：复用现有规则，吸收有效方法；不把外部提示词或研究系统原样搬入
- 实施记录（2026-10-18）：五类角色调整为“选项空间、成熟方案与复用、主张与时效、规则与例外、现实可行性”。将原设计中时效核验合并进主张审计，并把成熟方案侦察单列，以直接覆盖“漏掉现成做法”和“信息过时”两类不同痛点。该角色库是按需任务卡，不承诺独立 Agent 能力或效果提升。

## 1. 要解决的问题

减少信息差的关键价值，不只是从几个现成选项里挑一个，而是发现用户原先没有看到、且可能适合其真实目标与条件的路线；再核实重要信息，比较可行性并形成行动。

现有 Skill 已有澄清、选项扩展、搜索与来源检查、证据分级和决策比较等内容。已知问题说明，仅把规则写在文档里并不保证运行时会执行：回答可能在目标不清时先推荐；资料中的引文可能被拼接；产品版本会漂移；规则适用范围或例外会遗漏；热门方案也可能缺少真实成本、前提和可执行验证。

本次设计不再堆一份通用检查清单，而是为复杂问题提供边界清晰、按需启用的复核角色。角色负责调查一个可验证的问题，主 Agent 保留需求澄清、证据整合、推荐和最终答复责任。

## 2. 已知痛点与设计对应

| 已记录的痛点 | 证据来源 | 设计回应 |
| --- | --- | --- |
| 小生意的候选集容易只剩奶茶、咖啡、服装门店，看不到原料耗材、杯吸管、设备、配送和维修等位置 | 用户在本次需求中给出的具体例子；现有 `references/option-expansion.md` 已有相关扩展方法 | 选项空间侦察员按本题维度补充实质不同的路径，并明确哪些只是待调查假设 |
| Python 学习问题在没问学习目的、当前基础和约束前就直接给学习路线 | `life-guide-3.0.3-澄清优先修复记录.md`；用户对试用答案的明确反馈 | 主 Agent 把关键澄清作为研究前置门槛；不把用户目标判断外包给子角色 |
| 一次独立复核发现代理自检未发现的拼接引文 | 用户提供的独立复核记录及 `life-guide-3.0.0-独立复核与返修任务.md` | 主张与来源审计员回到来源原文，检查引文完整性、上下文与推论边界 |
| PDF 工具版本和功能信息漂移，旧条件可能改变推荐 | `life-guide-3.0.0-独立复核与返修任务.md`、`life-guide-3.0.1-复核结论与收尾任务.md` | 时效与版本核查员只核查会随时间变化且影响结论的事实，优先查官方当前资料 |
| 电商登记例外被漏掉；旧手机数据清除建议没有区分加密年代和设备条件 | 同上两份独立复核记录 | 规则与例外调查员明确法域、人群、版本、门槛和豁免，检查反向条件 |
| 用户不接受“听起来合理却不可行动”的建议 | 用户需求记录第 1、4、6、10 节及本轮反馈 | 现实可行性审查员把路径拆成前置条件、实际成本、验证动作和止损条件；证据不足就写未知 |

最后一项是用户明确的真实痛点，不代表当前系统已用大规模样本证明某一审查方法有效。

## 3. 吸收的成熟做法及边界

1. **独立判断和可更新判断**：参考已检查的 anti-sycophancy 与 ground-truth 类公开 Skill 的做法，保留“先按证据形成判断；有新证据时解释并更新”的原则。不照搬机械的反方仪式、每轮挑战或人格化措辞。
2. **拆分问题维度以发现不同路线**：借鉴价值链观察与形态分析的组织方法，按实际问题选择维度，找出被熟悉答案遮住的选项。不要求穷举维度、不追求组合数，也不把“陌生”当作“更优”。
3. **窄任务委派、主 Agent 综合**：OpenAI 的 Agent orchestration 文档将 manager 与 specialist handoff 作为一种可选结构；Anthropic 的多 Agent 研究经验也指出，任务边界和协调会影响重复、成本与效果。这里仅采用“有明确收益时才委派、任务范围清楚、主 Agent 综合”的设计原则；不把其内部评测结果外推成本 Skill 的效果保证。
4. **工作量与风险相称**：参考 UK Green Book 中按复杂度、成本和风险匹配评估力度、关注预测乐观偏差的方法。该文件的政府项目口径不直接套用到个人决策；本设计只借鉴比例原则和回看预测偏差的做法。

相关来源：

- [OpenAI：Orchestration and handoffs](https://developers.openai.com/api/docs/guides/agents/orchestration)
- [Anthropic：How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- [UK HM Treasury：The Green Book 2026](https://www.gov.uk/government/publications/the-green-book--2/the-green-book-2026)
- [Harvard Business School：The Value Chain](https://www.isc.hbs.edu/strategy/business-strategy/Pages/the-value-chain.aspx)

这些来源支持方法参考，不证明此设计一定提高效果，也不能代替对 Skill 的实际测试。

## 4. 方案比较与推荐

| 方案 | 好处 | 问题 | 结论 |
| --- | --- | --- | --- |
| 单 Agent 顺序自检 | 成本最低，宿主适用面广 | 独立复核弱；复杂搜索容易把路线发现、核实和适配混在一起 | 作为宿主不支持子 Agent 时的回退方式 |
| 每次固定启用五个 Agent | 表面上覆盖完整，流程看似统一 | 对简单问题过度；费用和时间上升；容易重复、相互矛盾，也无法保证所有宿主支持 | 不采用 |
| 宿主无关的专才角色库，按需委派；不支持时顺序执行 | 复用现有规则，复杂问题才增加复核；角色边界和交接可审计 | 增加少量调度规则；实际独立运行依赖宿主能力 | **推荐** |

推荐第三种。它是一份 Markdown 角色库和流程说明，不是新 Agent 平台，也不是五个必须安装的外部 Skill。宿主支持独立子 Agent 时，主 Agent 可按需委派；不支持时，主 Agent 依次按角色任务检查，并明确这不是独立复核。跨宿主可读不等于跨宿主行为已验证。

## 5. 设计目标与非目标

### 目标

- 遇到复杂、重要或可并行调查的问题时，按需启用明确任务的专才角色。
- 让选项扩展、来源核验、时效核查、规则适用范围和现实可行性分别得到关注。
- 主 Agent 先确保用户目标和个人约束足以支持个性化判断，再组织研究。
- 角色提供可追溯发现、反证、未知和对结论的影响；主 Agent 负责核验关键事实并给出综合判断。
- 不支持子 Agent 的宿主也能按同一角色说明顺序运行。
- 将每类角色的启动条件和不启动条件写清楚，避免把五角色变成固定仪式。

### 非目标

- 不建设可自动发现、安装、升级或运行任意插件的 Agent 平台。
- 不承诺任一 Skill 宿主都可创建子 Agent，也不宣称已跨宿主测试。
- 不自动登录用户账号、不访问未授权资料、不自动执行发帖等账号写操作。
- 不绕过验证码、登录流程、平台限流或风控；遇到这些情况使用现有工具访问规则处理。
- 不承诺穷尽所有选项、保证绝对最优、商业成功或 Star 数增长。
- 不更改用户的核心目标，不由子 Agent 代用户回答个人价值取舍。
- 不复制外部 Skill 的整段提示词或代码；只吸收可说明来源的通用方法。

## 6. 架构与工作流程

### 6.1 主 Agent 的职责

主 Agent 是唯一面向用户的协调者，应：

1. 理解本轮要解决的问题与用户已给信息，复用已有信息，不重复盘问。
2. 若目的、预期结果、当前基础或约束中有缺口，并且答案会改变个性化路线，则先向用户澄清并等待；不能把猜测标成“不阻塞”后继续个性化推荐。
3. 识别关键不确定点，并判断是否存在适合并行、且可由专才独立完成的工作。
4. 限定角色任务、允许使用的来源与输出格式，避免角色重复调查或擅自扩大权限。
5. 把角色发现视为调查线索；对足以改变建议的主张自行核验。
6. 统一事实、推断、未知与适用范围，去重并处理冲突；交付主推荐、有意义的备选、权衡和行动步骤。
7. 说明哪些复核已完成、哪些由于宿主能力或资料限制未做。

### 6.2 调度流程

1. **先澄清，后个性化研究**：调用现有 `needs-clarification.md`。角色库不创建第二套澄清规则。独立于个人状况的最低限度背景查证只有在帮助用户理解澄清问题时才可做，不能提前形成个人推荐。
2. **判断是否需要专才**：简单、稳定、低影响问题不启用；用户明确限定范围时尊重范围；复杂度、影响或关键不确定性达到实质程度时才选择对应角色。
3. **每个角色一个清楚任务**：说明问题、判断边界、可用来源和交付格式。仅并行处理彼此独立的工作；有依赖时按顺序做。
4. **按宿主能力运行**：可使用宿主提供的子 Agent 时才独立委派；否则在当前 Agent 内顺序执行，并将覆盖程度准确写清。
5. **综合与复核**：主要结论发生冲突时回到证据，不以投票解决。重要且会改变推荐的事实由主 Agent 复核；无法复核则降低结论强度或标记未知。
6. **交付并说明边界**：给用户看重要发现、来源与时间、适用条件、对选择的影响和未覆盖处；不展示无关内部角色对话。

不得因为“复杂”就自动启用所有角色。一个角色可能已经足够；有些任务没有必要委派。

## 7. 五个专才角色

五个角色对应五种不同的真实信息差，不意味着每次都要跑五轮或给用户五个新功能。

### 角色一：选项空间侦察员

**真实痛点：** 候选集被用户熟悉选项或 AI 最先想到的热门答案限制。

**任务：** 依据目标和边界，检查候选集是如何形成的；寻找会改变路线的不同参与位置、交付方式、成熟工具或进入路径。商业问题可按上下游、耗材、设备、渠道和配套服务等相关维度调查；学习、生活问题应换成该领域相干的维度。

**必须交付：** 新候选属于什么不同路线；为何可能相关；需要什么事实才能判断需求与适配；其证据当前是已证实还是待查。优先说明少量实质不同的路径，不堆同义名词。

**不做：** 不宣称穷尽，不因冷门而抬高，不把举例当成需求或盈利证据。复用 `references/option-expansion.md`。

### 角色二：主张与来源审计员

**真实痛点：** 引文拼接、断章取义、来源并不支持对应结论，或把推断写成原文事实。

**任务：** 对足以改变方案的具体主张回到最接近原始的来源；检查引文的逐字准确性、上下文、归属与推论链条；查找会实质改变判断的反证。

**必须交付：** 被审主张、来源链接及可定位位置、来源实际支持的范围、未支持的部分、冲突证据和对建议的影响。不能核实时写明原因。

**不做：** 不把搜索结果摘要当原文；不以更多引用数量代替来源质量；不将机械匹配误判当结论。复用现有搜索与证据记录规则。

### 角色三：时效与版本核查员

**真实痛点：** 版本、价格、政策、功能或供应状态变化后，旧信息仍影响推荐。

**任务：** 先判断某项事实是否会随时间变化且会影响选择；需要时查当前官方版本、日期、状态或变更记录，与回答中的版本和时间范围比对。

**必须交付：** 实际核查日期、权威来源、当前可确认信息、变化对方案的影响、仍然未知的部分。

**不做：** 不为静态常识强行实时搜索；不把当前最新版等同于适合用户；不从搜索摘要推断没有说明的兼容性或价格。复用 `references/search-playbook.md`。

### 角色四：规则与例外调查员

**真实痛点：** 只看一般规则而遗漏法域、人群、产品代际、门槛、定义或豁免。

**任务：** 对可能受规则或条件约束的建议，明确法域、适用对象和日期，查找定义、豁免、例外、过渡条款及执行边界。对于产品与设备，检查版本/年代和安全机制差异。法律内容只说明有出处的文本和不确定性，不冒充法律意见。

**必须交付：** 适用规则及其范围、与用户场景的对应关系、相关例外、未知事实、足以改变结论的条件。来源不足或法域不清时标记需补信息。

**不做：** 不把别的法域或旧版本规则套用；不把“未找到”说成“不存在”；不以一般网页摘要替代正式文本。

### 角色五：现实可行性审查员

**真实痛点：** 推荐有道理但无法行动，隐藏成本、获客、时间、设备、资质或退出代价没被计算。

**任务：** 站在目标使用者的现实条件下，拆出一条路线的前提、现金与时间成本、能力/许可要求、获取资源的途径、失败损失与可逆性；寻找低成本验证方式和继续/停止条件。对商业机会区分需求证据、用户假设和待验证数据；不以行业热度代替本地客户证据。

**必须交付：** 现在可试/满足条件后可试/当前不适用的判断依据；最重要的缺口；最小验证动作；观察指标与停止条件；会改变推荐的条件。

**不做：** 不捏造本地市场规模、转化率、收入和成本；不把无资源解释成永远不可行；不把小测试的结果夸大成成功保证。

## 8. 角色统一交接格式

每个角色以简短结构化结果交还主 Agent：

1. **任务边界**：实际检查了什么、没检查什么。
2. **关键发现**：只报告与任务有关的发现。
3. **证据**：来源链接、名称、日期或可定位段落；引用保持原意和上下文。
4. **适用范围**：法域、对象、版本、时间、前提等相关边界。
5. **反证与未知**：有哪些相反证据、未能验证的点。
6. **对决策的影响**：什么条件会改变候选排序或推荐。
7. **下一步验证**：如仍缺证据，给出一个实际可执行的查证动作。

禁止只交“建议选 A”而无理由、来源和适用条件。角色不能把自己的概率、观点或模型生成的解释包装成外部证据。

## 9. 隐私、权限与工具边界

- 子 Agent 只能获得完成其任务所需的最少上下文；避免传递无关个人隐私、账号材料或整份个人知识库。
- 用户提供的材料可按本轮目的分析；角色不得据此擅自保存、分享或执行外部写入。
- 只有宿主已提供并授权的检索/工具可用。角色不自行安装插件或索要密码、Cookie、Token。
- 确实缺少工具时，主 Agent 可说明可选工具和用途；工具访问规则以 `skills/life-guide/references/tool-access.md` 为准，通用维护纪律见 `docs/maintainers/CONTRIBUTING.md`。
- 不尝试绕过验证码、登录校验、风控或速率限制；受阻时停止该自动访问路径，继续可用来源并披露缺失范围。
- Agent 输出不自动可信。敏感数据不因“并行”而扩散。

这些边界与现有授权要求一致，不代表新授予任何平台或账号权限。

## 10. 验收方案

验收看行为、来源和决策适配，不看文件里是否有某个关键词，也不把“列出五个选项”当成通过。建议使用现有失败记录和合成测试提示构成离线回归包；报告清楚注明哪些是历史真实问题、哪些是模拟场景。

| 场景 | 验收要求 |
| --- | --- |
| 目标不明的 Python 学习问题 | 不先给个人化路线；先问目的、目标结果、当前基础及关键约束，并等待答复 |
| 小生意候选集 | 能从门店扩到至少一个实质不同的位置/交付路径；清楚标记待查，不把原料、设备等直接说成商机 |
| 软件工具版本 | 对影响建议的易变版本查官方当前来源并记录核查日期；若无法访问，说明不确定性 |
| 规则与产品例外 | 检查法域/适用人群/版本，并寻找可改变结论的定义、门槛或豁免 |
| 引文准确性 | 将重要引文回查原始上下文；识别拼接、遗漏改变原意或来源不支持；清楚区分原文与推断 |
| 路线可行动性 | 识别至少一个会阻断执行的现实条件，给有依据的最小验证或说明尚缺数据；不编造市场数字 |

还须验证调度边界：低复杂度、信息充分的问题不会机械启动五角色；缺少子 Agent 能力的模拟环境会按序执行并如实标为非独立复核。测试结果要保留样本输入、实际输出或判定记录、发现与未验证项。少量样例仅支持“这些样例表现如何”，不支持普遍效果结论。

## 12. 半天工作量估计与风险

以单人约四小时的实现和验收为目标：30 分钟对照规则和确定角色边界；60 分钟接入 Skill 路由与角色参考；60 分钟制作并运行现实样例；45 分钟人工复核证据、失败行为和宿主回退；30 分钟同步 README、需求镜像、变更记录与验收报告；约 15 分钟机动。这个估计不包含多平台安装和实测，也不承诺四小时内解决外部宿主限制。

主要风险：

- 有些宿主不提供可控子 Agent；角色库在这些宿主上仍是顺序自检，独立性较弱。
- 多 Agent 可能增加成本和等待，并产生重复或冲突；因此调度必须有清楚收益。
- 子 Agent 可能误引或误读资料；因此关键结论要由主 Agent回查，不能靠多数表决。
- 固定角色覆盖不了所有知识领域；遇到缺少专业来源或无法验证时应报告未知。
- 角色卡无法保证模型执行率或找到用户此前不知道的信息；需在目标宿主进行真实用例验证。
- 五个回归用例只能发现已构造的失败模式，不足以代表所有用户和场景。
