# 发布计划与观察指标

## 目标口径

- **保底 500 star 是工程化目标**，靠定位清楚、第一公里顺畅、渠道覆盖来争取。
- **2000 star 只是传播目标，不是承诺。** 它通常需要一次外部放大（社区热帖、榜单、转发），不作为验收通过条件，不写进 README，不用于对外宣传。
- 功能验收只认真实证据：安装、触发、参考读取、行为输出、复现失败记录。

## 发布前清单

- [x] zip 顶层为 `life-guide/`，包内含 LICENSE
- [x] frontmatter 含 `license: MIT`，版本与 CHANGELOG 一致
- [x] 结构 CI 六项通过
- [x] 公开材料无私有路径、无夸大承诺
- [x] README 含定位、安装命令、自验问题、验证边界、贡献方式
- [ ] 推送到公开仓库并打版本 tag（需维护者远程权限）
- [ ] 准备一组前后对照演示（同一问题，无技能 vs 有技能，标注边界）
- [ ] 发布后按平台逐项补实测状态

## 渠道建议（按投入产出排序）

1. 直接相关社区的主题分享：聚焦一个真实问题的前后对照，不发「请给我点星」。
2. awesome 类清单 PR：按各清单的贡献要求提交，描述写清适用与不适用。
3. 开发者社区（Reddit / Hacker News / V2EX / 掘金 / 即刻）：同一素材按社区规则改写，不群发同文。
4. 官方或聚合目录：按各平台要求提交；WorkBuddy 开放平台需专用宿主包，豆包需企业认证与审核。

发布时间只是弱信号，不迷信某个整点；发布后 48 小时内及时回复问题比发布时间更重要。

## 发布后观察指标

| 指标 | 看什么 | 异常信号 |
|---|---|---|
| 安装成功率 | 各宿主能否列出名称与描述 | 同一平台多人装不上 → 优先修安装文档 |
| 首次运行完成率 | 第一条测试问题是否符合预期形态 | 简单事实也启动调查 → 触发边界问题 |
| 触发准确性 | 25 条触发样本的召回与误触发 | 误触发 >5% → 回查 description |
| 故障分类占比 | 装不上 / 不触发 / 读不到 / 答非所问 | 某类集中出现 → 定位唯一责任文件 |
| 复现失败报告数 | 按 README 仍跑不通的报告 | >0 即需复盘 README |
| 传播参考值 | star、fork、下载、外部贡献者 | star 涨但 fork / issue 不动 → 围观流量，不庆祝 |

## 复盘纪律

- 渠道全绿但 star 不达标：是选题或时机问题，不改技能本体。
- star 达标但行为证据崩：暂停推广，先修问题。
- 不用刷量、互换星标或购买星标；那会直接污染上面所有指标。
