# 维护与贡献

## 修改顺序

1. 先确认当前源包、版本和引用关系，不按旧行号覆盖。
2. 说明要解决的用户可见问题，区分已观察证据、假设和方案选择。
3. 行为修改先写清通过/失败案例，再编辑规则；多个维护者可并行审阅，但同一文件同一时间只设一个写入者。
4. 检查入口和引用文件是否冲突，个人资料与开发任务是否误入发行包。
5. 运行 Agent Skills 格式校验和仓库结构检查；行为案例由人工检查实际对话，不以关键词脚本代替语义判断。
6. 记录变更、验证范围和未验证项。完成本地检查不代表宿主兼容或效果已证明。

## 设计边界

- 保持一个通用核心和按需加载的细则，避免再建第二套主流程。
- 每项角色/模块只解决已记录的痛点；简单问题不强制进入多 Agent 流程。
- Agent 角色输出是线索；关键事实回到原始来源核验，由主 Agent 综合。
- 不复制外部项目的长段提示词或代码；只吸收可说明来源的方法，并保留适用边界。
- 不把个人需求、账号凭证、私有路径和内部对话纳入公开发行包。
- 发布前必须确认许可证、作者身份和目标宿主验证范围。
